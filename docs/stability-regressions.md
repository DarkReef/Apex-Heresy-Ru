# Воспроизводимые регрессии стабильности

Проверки используют синтетические документы и реальные функции системы. Живые миры и базы в этом аудите не изменялись.

## Повторное применение состояния после собственного таймера — P1

Воспроизведение: собственный срок состояния `stunned` истёк; новый эффект оружия вызывает `addCondition('stunned', {rounds:3})`. Foundry объединяет вложенные данные обновления, поэтому прежние `duration.expiry = darkHeresyBoundary` и `flags.dark-heresy.effectClock` сохранялись вместе с новым сроком в три раунда. Состояние затем зависело от старого боя и старого срока вместо новой длительности.

Красная проверка `reapplying a dormant condition with a new native duration discards its old custom expiry schedule` подтвердила сохранение `darkHeresyBoundary`. Исправление явно очищает старый собственный таймер и назначает нативное событие истечения при задании новой нативной длительности; после правки проверка проходит. Проверка находится в `tests/stability-regressions.test.mjs`.

## Отключение эффекта продлевало абсолютный срок — P2

Воспроизведение: назначить срок до следующего начала хода цели, отключить эффект перед этим ходом и включить после него. Обработка срока пропускала `disabled`-эффект, позволяя возобновить его до следующего такого же события.

Красная проверка `a manually disabled scheduled effect still expires at its deadline and cannot revive one round late` получила `duration.expired = false` вместо `true`. После удаления проверки `effect.disabled` из расчёта наступившего срока она проходит: отключённый эффект также помечается истёкшим. Уже истёкшие эффекты по-прежнему пропускаются; простой переключатель не возобновляет срок. Отдельная проверка подтверждает, что явный перезапуск создаёт новый срок и эффект затем завершается на новом событии.

Команда: `node --test --test-isolation=none tests/stability-regressions.test.mjs tests/effect-clock.test.mjs`.

## Смена активного GM до исполнения запроса — P1

Воспроизведение: `processRequest` ставит действие в очередь, затем до запуска операции меняется активный GM. `executeRequest` возвращал управление без операции, а внешний обработчик помечал запрос завершённым. Строка боевой карточки оставалась без изменения; новый GM уже пропускал такой завершённый запрос.

Красная проверка первоначально зафиксировала одновременно исходную фазу `reaction` и статус запроса `complete`. После исправления утрата полномочий до исполнения либо после операции оставляет запрос ожидающим; неактивный GM не записывает подтверждение или ошибку. Новый GM может обработать тот же запрос. Уже завершённая операция распознаётся по сохранённой квитанции и не вызывает повторной мутации. Если подтверждение нативной операции потеряно, запрос требует ручной проверки и не запускает её повторно.

Зелёные проверки покрывают смену GM до исполнения, подтверждение уже применённого урона новым GM без повторного применения и потерю подтверждения после возможной мутации. Профильный набор `stability-regressions`, `effect-clock`, `foundry-attack-workflow`, `attack-workflow`: **55/55 прошли**. Это автоматические проверки жизненного цикла и идемпотентности, не замена живому многопользовательскому прогону.

## Поля расширений после перезагрузки — P1

Полная перезагрузка обнаружила отдельный разрыв жизненного цикла: ItemPileFFG расширял модели в событии `setup`, а Foundry 14 создаёт документы мира до этого события. Поэтому существующие контейнеры, количества, цены и кошелёк могли попасть в `system.legacyData`, после чего лист видел стандартные значения вместо сохранённых. Дополнительно миграция системы сравнивала поля только с исходным `template.json`, не учитывая зарегистрированные поля подкласса расширения.

Исправления согласованы с порядком загрузки: модель системы регистрируется синхронно; `darkHeresy.dataModelsReady` даёт расширению возможность добавить поля до создания документов мира. Для синхронного старта используется `script/data/template-data.mjs`, генерируемый из `template.json` командой `npm run models:build`. Проверка совпадения обоих файлов входит в обычный `npm test` и CI.

Миграция теперь проверяет фактическую `this.schema`, включая вложенные поля расширений и свободные `ObjectField`-карты. Историческое исправление числовых массивов ориентируется на зарегистрированный тип поля. Неизвестные данные по-прежнему архивируются. Ранее созданный архив сохраняется; живые значения не заменяются архивными автоматически.

Четыре новые проверки миграции сначала падали, затем прошли после исправления. Вместе с прежними проверками моделей и совпадения сгенерированных данных — **11/11 прошли**. Отдельная проверка на реальных моделях Foundry 14.368 и настоящем расширении схемы ItemPileFFG подтвердила сохранение количества 7, цены 32, ссылки на рюкзак и кошелька 55 после сериализации и повторного создания документа; обращение к базе в проверке запрещено. Свежие QA-документы после развёртывания требуют отдельной проверки полной перезагрузкой.

### Проверка ранее архивированных данных без записи

Для старых пострадавших документов сначала готовится отчёт, без вызовов `update`, `create` или `delete`:

1. Взять резервную копию исходных сохранённых документов и сравнить её с текущей схемой расширения. Подготовленные значения листа и стандартные значения, уже добавленные очисткой модели, не доказывают наличие значения в исходной записи.
2. Для каждого поля архива показать UUID документа, путь, архивное значение, наличие **собственного поля в исходной сохранённой записи**, текущее значение и соответствующий зарегистрированный тип.
3. Рассматривать как возможное восстановление только поле, распознаваемое текущей схемой и отсутствующее в исходной записи. Явно сохранённые `0`, пустая строка, `{}`, `[]`, `false` и `null` являются текущими данными; их нельзя заменять архивом только потому, что они похожи на значения по умолчанию.
4. Проверить предлагаемый документ на копии через нативную модель. Ссылки на контейнеры должны указывать на существующие предметы того же владельца; необходимы проверки циклов и количества. Неизвестные поля не восстанавливаются как активные поля схемы.
5. Мастер проверяет конкретный отчёт и резервную копию до адресного восстановления. Архив сохраняется. При отсутствии исходного сохранённого источника, наличии конфликта или невозможности отличить явный сброс от значения по умолчанию автоматическое восстановление не выполняется.

Этот выпуск не запускает массовое восстановление `legacyData`: назначение архива — сохранить данные для проверяемого решения, а не молча отменить более поздние правки пользователя.

## Служебные карточки боевого журнала в чате — P2

Живая проверка Foundry 14 выявила пустые слепые карточки служебных запросов, иногда с кнопками применения урона и лечения. Атрибут `hidden` перекрывался стилем `display:flex` у `li.message`; основной обработчик чата также добавлял обычные кнопки до проверки служебного запроса.

Две красные проверки воспроизвели сохранение `display:flex` и выполнение обычных обработчиков для `combatWorkflowRequest`. Исправление задаёт контейнеру `style.display = "none"` и завершает основной обработчик до добавления кнопок. Это изменение отображения: документы запросов, доказательства бросков и квитанции завершения сохраняются для проверки и восстановления активным GM.

Профильные проверки `stability-regressions` и `foundry-attack-workflow` после исправления проходят; отдельная проверка сохраняет обычную обработку настоящих карточек броска. Проверки запускаются без живого мира. Результат скрытия в настоящем интерфейсе отдельно проверяет основной агент.
